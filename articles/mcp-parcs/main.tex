% Abstract
\abstract{%
Large language model (LLM) agents have demonstrated impressive capabilities in tool use, code generation, and scientific reasoning, yet they remain bound by the throughput of a single execution thread. Computationally intensive tasks—Monte Carlo simulation, combinatorial optimisation, hyperparameter search, large-scale graph analysis—either time out or require severe undersampling when handled sequentially. We present PARCS-Agent, a system that exposes a cloud-scale distributed computing cluster to an AI agent through three Model Context Protocol (MCP) tools: \texttt{get\_cluster\_info}, \texttt{create\_session}, and \texttt{run\_layer}. The agent submits arbitrary C\# computation logic; the platform compiles it with Roslyn at runtime, fans it out across up to 21 Kubernetes worker pods via Google Cloud Pub/Sub and KEDA autoscaling, and returns aggregated results. We introduce the PARCS-Agent Benchmark, a suite of 15 tasks spanning quantitative finance, bioinformatics, epidemiology, machine learning, cryptography, and atmospheric science, designed so that the sequential wall-clock cost substantially exceeds practical agent time budgets. Experiments show that PARCS-enabled agents achieve mean speedups of 15--18$\times$ over sequential baselines while delivering statistically equivalent or superior solution quality. PARCS-Agent is, to our knowledge, the first system to use MCP as the interface between an AI agent and a live distributed HPC cluster, and the first benchmark to measure \emph{speedup ratio} as a first-class agent capability metric.%
}

\section{Related Work}
\label{sec:related}

\subsection{Tool-Augmented Language Model Agents}

Early work on augmenting language models with external tools showed that models could learn, without supervised labels, when and how to call a calculator, a search engine, or a translation API~\citep{ref-toolformer}. ReAct extended this idea by interleaving reasoning traces with actions such as web lookups and database queries, showing that grounding reasoning steps in real observations leads to better task completion~\citep{ref-react}. Both papers treat tools as stateless, single-call functions that return a value and exit - a model that works well for retrieval and simple arithmetic but does not fit long-running or parallelisable computation.

Later systems scaled tool use to much larger API surfaces. ToolLLM~\citep{ref-toolllm} trained a model to navigate a collection of 16{,}000 REST endpoints, while Gorilla~\citep{ref-gorilla} addressed the specific problem of hallucinated API signatures in ML framework calls. SciAgent~\citep{ref-sciagent} moved into scientific reasoning, wrapping domain algorithms as callable tools across mathematics, physics, and finance. Mialon et al.~\citep{ref-augmented-survey} survey the broader landscape and categorise augmented language models along the dimensions of memory, reasoning, and action; they note computation as a relatively underexplored tool type. What all these systems share is that each tool call is local, synchronous, and bound to a single process. PARCS-Agent takes a different route: \texttt{run\_layer} submits user-written C\# code to a Kubernetes cluster, fans it across up to 21 concurrent workers, and returns their aggregated output - the tool itself is a distributed job.

The closest prior work in terms of parallelism is LLMCompiler~\citep{ref-llmcompiler}, which analyses a user query, builds a dependency graph of tool calls, and runs independent branches simultaneously. This cuts latency by up to $3.7\times$ on multi-hop question answering. The difference is that LLMCompiler parallelises \emph{calls to existing tools} - running several web searches at once, for instance. It does not compile new code or provision workers. CodeAct~\citep{ref-codeact} goes further by treating Python code as the agent's universal action, running it in a persistent interpreter that accumulates state between turns. Execution is still single-threaded and local; PARCS-Agent compiles the submitted code once and distributes the binary to remote pods, which run in parallel.

\subsection{LLMs for High-Performance and Parallel Computing}

The question of whether LLMs can write parallel code has received growing attention. Nichols et al.~\citep{ref-pareval} benchmark code generation in MPI, OpenMP, CUDA, and Kokkos across 420 problems and find that correctness rates drop sharply compared to equivalent serial implementations, particularly as problem complexity grows. HPC-Coder-V2~\citep{ref-hpccoder} tries to close this gap by fine-tuning on a corpus of 120{,}000 synthetic parallel code samples and reports gains on MPI and OpenMP generation. Separate work evaluating frontier models on classical HPC kernels - conjugate gradient, matrix multiply, and similar - found that even strong models struggle with non-trivial memory access patterns~\citep{ref-deepseekhpc}.

PARCS-Agent sidesteps the parallel code generation problem entirely. The agent writes only per-worker logic as a plain C\# class; the platform takes care of thread scheduling, inter-pod communication, and result collection. This means the agent never needs to reason about synchronisation or data decomposition at the code level - it just describes what a single worker should do, and the runtime handles the rest. The gap identified by ParEval is real but becomes irrelevant when the parallel infrastructure is a managed service.

He et al.~\citep{ref-legionllm} use LLMs to automate mapper optimisation in the Legion distributed runtime, replacing expert tuning that previously took days. This is a legitimate and useful application, but it assumes a parallelised program already exists and targets a narrow optimisation problem. PARCS-Agent is concerned with an earlier stage: an agent that has no pre-existing parallel program and wants to run a new computation in parallel from scratch.

\subsection{Agent Benchmarks for Computational Tasks}

Several benchmarks now measure how well agents handle complex, multi-step tasks. GAIA~\citep{ref-gaia} uses 466 real-world questions that require web browsing, file reading, and multi-modal reasoning; the hardest questions remain largely unsolved. SWE-bench~\citep{ref-swebench} measures whether agents can resolve real GitHub issues by producing patches that pass existing tests, with top systems now clearing around 50\% of the verified subset. ScienceAgentBench~\citep{ref-sciagentbench} focuses on data-driven science, drawing 102 tasks from 44 published papers across bioinformatics, chemistry, GIS, and psychology; the best agent manages about a third of them. TheAgentCompany~\citep{ref-agentcompany} simulates workplace tasks including software engineering and data analysis.

What none of these benchmarks test is whether an agent can exploit parallelism to get more done. Every task is designed to be completable sequentially, and wall-clock time is at most a secondary concern. The PARCS-Agent benchmark is built around the opposite premise: each of the 15 tasks requires compute that is impractical to complete in sequence within a reasonable budget. The gap between sequential and parallel agents is therefore the central result, and speedup ratio is reported alongside solution quality. Using speedup as a primary agent evaluation metric is, to the best of our knowledge, new.

\subsection{The Model Context Protocol}

Anthropic introduced the Model Context Protocol (MCP) in 2024 as a standard JSON-RPC-over-SSE interface for connecting LLM agents to external tools and data sources~\citep{ref-mcp}. Hou et al.~\citep{ref-mcpsurvey} survey the ecosystem and flag security concerns around prompt injection and tool poisoning, but find no work on using MCP to front distributed compute infrastructure. A separate study of published MCP tool descriptions found that more than half lacked adequate documentation of purpose or parameters~\citep{ref-mcpsmell}; this influenced the design of the PARCS-Agent tools, which include explicit parameter bounds and example values in their descriptions.

No prior work appears to have used MCP as the interface between an AI agent and a live HPC cluster. PARCS-Agent is the first system to do so, and the first benchmark designed to measure agent performance specifically on tasks where parallel compute access is the deciding factor.
